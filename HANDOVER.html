System overview and architecture

Remote Hustle is one Next.js/TypeScript application with a public website, worker workspace, administrator workspace and server endpoints. React renders the interface. Its current styling uses the supplied CSS design system; Tailwind and Lucide were suggestions, not installed runtime dependencies.

ServiceResponsibility
VercelNext.js rendering, route handlers, server actions and scheduled maintenance.
SupabasePostgres records, email/password authentication, verification and password reset. Row-level security and checked SQL functions enforce access.
Cloudflare R2Private CVs/digital resources and public website images/logos. Private file links expire after two minutes.
Cloudflare TurnstileOptional configured authentication CAPTCHA and mandatory production contact-form bot checks.
BrevoOne company-owned RH account: SMTP configured in Supabase for authentication; separate API credentials for application and purchase email.
PaystackHosted payment collection behind the payment-provider module. The server verifies amount, currency and reference before granting paid access.
Company GitHubSource ownership, CI checks and optional encrypted backup workflow.

Browser requests reach Next.js. Ordinary account/admin operations use the signed-in Supabase session and database permissions. Narrow server-only operations use the service-role key: verified file finalisation, payment reconciliation, contact intake and background delivery. Never move the service-role key into browser code.

Authoritative paths: src/app routes; src/components interface; src/actions server actions; src/lib auth, business rules and integrations; supabase/migrations schema; scripts maintenance; tests automated checks. package-lock.json pins exact dependencies.

Company setup and production activation

  1. Ownership. Create/use company-owned GitHub, Vercel, Supabase, Cloudflare, Brevo and Paystack accounts. Add named staff with the least permissions they need. Enable MFA and store recovery codes with company management. No critical asset should depend solely on your personal mailbox.
  2. GitHub. Create the private company repository, push the complete source including the lockfile, migrations, templates, scripts and workflows. Verify another authorised company member can access it. Set branch protection/review rules and run the App checks workflow. Never commit environment files, private customer files or decrypted backups.
  3. Hosting. Import the repository into the company Vercel project. The root must be the folder containing package.json. Configure production environment variables. Add remotehustle.plug99com.ng and create the exact DNS records Vercel shows; do not change mail MX records. Check HTTPS, redirects and the site's canonical host. Use the agreed commercial hosting plan at public launch.
  4. Supabase. Apply migrations through 013. Keep only public exposed through the Data API. Enable email confirmation; set minimum password length to 12. Set Site URL and redirect https://remotehustle.plug99com.ng/auth/confirm. Use separate staging and production projects. Review Auth rate limits.
  5. Email. Authenticate the company's sender/domain using the exact DNS records Brevo provides. Do not create duplicate SPF records. Enter Brevo's SMTP host, port, username and SMTP key in Supabase; enter a Brevo API key only in the app's server environment. Copy confirmation/recovery/invitation HTML from supabase/templates. Verify all six requested emails: verification, reset, welcome on approval, order confirmation, download link and application status. Invitations are an additional template. Check inbox and spam placement and provider delivery logs.
  6. Bot protection. Create a managed Turnstile widget, allow the real site hostname and your separate development hostname. Put its site key in the public variable and secret in TURNSTILE_SECRET_KEY. Configure the same provider secret under Supabase Auth CAPTCHA. Auth tokens go to Supabase; contact tokens are checked on the server for hostname/action. On production, contact submission refuses to store a message if CAPTCHA is unavailable. There is no production bypass flag. Without the site key, auth CAPTCHA remains off until the dashboard and app are configured together.
  7. Files. Use distinct private/public R2 buckets. Disable all public access to the private bucket. Configure the public image domain. Use the CORS origins in SETUP.md with the actual production hostname. Verify mobile CV upload, digital file upload, signed download expiry and access denial from another account.
  8. Payments. Activate the company's Paystack account. Set the live secret only on production. Configure webhook https://remotehustle.plug99com.ng/api/payments/webhook. The app constructs its callback at /api/payments/callback. Test one approved low-value live purchase and inspect the provider reference, order, download and email. A browser success redirect alone is not proof of payment.
  9. Owner and content. Create and verify the intended owner account; for a new database run npm run bootstrap-owner -- verified-company-email. It refuses to create another initial owner if one already exists. Invite individual admins and assign their areas. Publish real lists, jobs, programmes, partner logos, About/contact copy, permitted testimonials, products and the purchase support/download policy.
  10. Operations. Configure CRON_SECRET, check daily invocations, set up an external monitor for /api/health, activate and verify backups, and submit the sitemap in company-owned Search Console. Add the supplied Google verification token or use DNS verification.

npm run check-config checks presence and basic shape, not whether a provider account works. npm run smoke-check -- https://remotehustle.plug99com.ng performs read-only HTTP checks; it cannot certify payments, inbox delivery or recovery.

User guide

  1. Sign up with your name, email and phone, acknowledge the policies, then verify your email. Resend is available if the email expires or is missing.
  2. The team reviews pending accounts. An inactive account cannot use protected actions.
  3. Open your workspace and complete every profile item, including location, category, skills, experience, education, CV, professional link and preferences. The progress indicator explains missing details.
  4. Find work and open a role. Internal applications use your profile/CV and optional cover note. External roles continue to the employer website only after the required account checks; their outcome is not tracked as an internal submission.
  5. Browse digital resources. Add products to your cart or follow a shared purchase link. Review items, any discount and the published policy. Sign in, verification, approval and profile completion are required before checkout.
  6. Continue to Paystack. If payment is pending, check status; do not assume you must pay again. Failed payments offer a retry. Confirmed orders expose downloads in Workspace → Orders, and service emails link to that authenticated order page.
  7. For a download, file or payment problem, select Report a purchase issue on the order. Read the team's reply there. General contact messages can be submitted on About; the team replies by email.

A shared product link is an app purchase page, not an unrestricted Paystack Payment Page. It preserves the required customer checks and automatic fulfilment. If management later requires payment links for services not represented by digital products, define those services and their delivery workflow first.

Database and integration contracts

Migrations 001–013 create 33 public application tables with row-level security. Identity comes from auth.users; profiles, skills, worker approvals and administrator memberships control access. Jobs/applications retain application status history. Product/media records link immutable private files to order items. Orders, payment attempts, corrections and email outbox entries implement fulfilment and retries. Contact messages are private to content admins. Maintenance status is visible only to the owner.

private.contact_rate_limits is not exposed by the API. Contact submissions are limited to five successful requests per network/email key per hour using server-generated keyed hashes; expired keys are removed by subsequent submissions. On non-Vercel hosting the network bucket is shared until a trusted proxy strategy is explicitly implemented. An anonymous browser cannot call the submission RPC directly.

New SQL functions: submit_contact (service only); review_contact (content permission); admin_analytics (scoped counts); admin_operations and retry_failed_email (super admin). admin_attention now includes contact messages, failed emails and stale/missing maintenance. Ordinary admins cannot read arbitrary email payloads through the operations page.

Server actions in src/actions handle forms with fresh permission checks. Do not treat their internal Next.js transport as a public REST API. The route inventory below lists the explicit endpoints. Most mutation endpoints validate the request origin and authenticated identity; callback/webhook/cron routes have their own authentication mechanisms.

Backup and restoration runbook

Code is supplied; no real production backup or restore has been performed here. A green encryption test does not prove that your company's database can be recovered.

  1. Choose a company-owned backup runner with Node 22+, Docker and Supabase CLI. Keep it separate from the web runtime. Grant R2 credentials read-only access to both source buckets. Store the database connection string as BACKUP_DATABASE_URL and a random 64-hex-character key as BACKUP_ENCRYPTION_KEY. Store that key separately from backup archives with a second authorised company custodian.
  2. Run npm run backup. It exports roles/schema/data, includes this app's custom auth-trigger restore file, and copies public/private R2 objects except temporary staging objects. Each file and the manifest are AES-256-GCM encrypted. A COMPLETE marker is written only after all exports succeed. Database SQL temporarily exists in a restricted local temp folder and is removed in the normal exit/failure path; use a trusted encrypted runner and clean up after machine crashes.
  3. Run npm run verify-backup -- .backups/TIMESTAMP. It authenticates/decrypts every entry and checks hashes without retaining plaintext. Keep only verified complete snapshots.
  4. To automate, set company-repository variable ENABLE_SCHEDULED_BACKUP=true, create the backup GitHub environment, and populate the secrets named in .github/workflows/backup.yml. It runs at 03:30 WAT daily and retains encrypted artifacts for 14 days. GitHub storage quotas and workflow scheduling still apply. Enable failure notifications and assign someone to check the last successful run. Keep longer-term independent copies if company policy requires them.
  5. For a restore drill, use a new, isolated Supabase project and new public/private R2 buckets. Disable outgoing mail, payment webhooks and cron on the restored environment. Do not run a restore against production.
  6. Extract with npm run verify-backup -- .backups/TIMESTAMP --extract restore-output. The destination must not exist. Copy SQL entries to their recorded names using the manifest as shown below.
  7. Restore SQL using the official Supabase procedure. Review roles/schema for managed-role differences and extensions. Keep triggers disabled during data import, then apply auth-triggers.sql. Do not rerun migrations on top of a schema restored from the same snapshot. If your production setup uses Supabase CLI migration history, export and restore supabase_migrations separately according to the official guide; these snapshots do not claim to preserve that platform history.
  8. Restore R2 using the separate script with new destination credentials. It refuses source bucket names and refuses to overwrite existing objects. Reconfigure image domains/URLs in the isolated site and verify private access remains private.
  9. Verify account sign-in (using authorised test accounts), profile/CV access, product files, historical orders, role isolation and row counts. Create a new test account to verify both auth triggers. Record who performed the drill, snapshot timestamp, duration, missing data and any issues. Only then mark the restoration requirement complete.

$m = Get-Content manifest.json | ConvertFrom-Json

The R2/database snapshot is not a cross-service transaction. Avoid schema changes and deletion/replacement of files during a critical pre-launch snapshot; perform the restore drill to detect broken file references. It excludes deployment secrets, DNS, SMTP settings, Turnstile settings, Paystack configuration and any Supabase Vault root keys. Those need the separate secured account/configuration inventory. The script does not automatically prune local snapshots. Define retention, delete expired archives and securely remove extracted plaintext after the drill.

Official procedure: Supabase backup and restore. Custom auth triggers are restored from supabase/restore/auth-triggers.sql.

Maintenance and incident handling

Frequency / symptomAction
DailyCheck admin attention, purchase issues, pending payments, contact inbox, failed emails, cron completion, uptime and successful backup artifacts.
WeeklyReview admin access, provider quotas, failed delivery logs, stale jobs and product files. Inspect CI/dependency security reports before updating packages. Export required operational records through approved channels.
Monthly / after major changesPerform an isolated restore drill, review retention, validate mobile journeys, rotate exposed credentials and rehearse rollback. Record evidence.
Order/page errorRead Vercel server logs. Database diagnostics identify the failing table/code without order contents. Check connection status and whether all migrations are installed. Do not disable access rules or return fake empty paid records.
Email not receivedSeparate Supabase SMTP/auth email from app API/outbox email. Check sender authentication, rate limits, provider rejection/spam logs and Operations. Retry only after checking prior acceptance.
Payment pendingUse Payment checks and compare the reference against Paystack. An uncertain request is not automatically a failed charge. Do not generate a second charge or issue another correction without checking the first.
Contact unavailableCheck Turnstile allowed hostname, site/secret pair, contact secret length, migration 013 and server logs. Email contact remains available. Do not remove server verification to silence an error.
File upload failsCheck signed-link expiry, type/size, R2 CORS, credentials, network and private-bucket access. Re-upload after a failed finalisation. Never expose the private bucket to fix a download problem.
After a bad deploymentRoll back the app to the last compatible revision in Vercel. Additive migration 013 can remain while rolling back code. Never drop new tables in a rush or restore an old database over new paid orders. Escalate data recovery separately.

The health endpoint confirms database reachability only. It does not test email, payments, storage or backup freshness. Daily maintenance is best effort, not a guarantee that free-tier services stay active. At higher volume, monitor queue sizes and increase delivery/reconciliation frequency on the approved hosting plan.

File signature validation and image re-encoding are implemented; antivirus/content scanning of documents and ZIPs is not. Before opening uploads broadly, agree the company's malware-scanning service or document the accepted limitation. No external security certification or penetration test is claimed.
